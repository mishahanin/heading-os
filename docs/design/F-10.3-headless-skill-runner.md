# ADR F-10.3: a headless skill runner that structurally cannot send

Design record for Phase 10 item F-10.3: how to run a HEADING OS skill non-interactively from the command line, reusing the F-10.1 `heading` CLI surface, without ever letting an unattended run cross the outbound send gate.

Last Updated: 2026-07-17
Status: accepted

## Context

A skill today runs only inside an interactive Claude Code session: a human types `/state-check`, watches, and approves. That blocks three things the engine wants: scheduled runs (a nightly `state-check` with no human at the terminal), scripted composition (a daemon or another skill invoking one headlessly), and CI-style checks. F-10.1 already shipped the invocation surface this rides on: the thin `heading` CLI, plus the data seam (`WORKSPACE_ROOT` + `HEADING_OS_DATA`) that resolves a bundled or demo data root. F-10.3 adds the missing verb: run a *skill*, not a script.

The headless mechanics were verified live against the local `claude` binary (v2.1.201) and the official docs (code.claude.com/docs). The load-bearing facts:

- `claude -p "<prompt>"` (`--print`) runs one prompt non-interactively and exits. `--output-format` accepts `text` (default), `json` (a single result envelope), or `stream-json`. The JSON envelope's exact field names are not published, so the design treats them as best-effort enrichment, never the primary signal.
- A slash command passed as the prompt (`claude -p "/state-check"`) fires that skill deterministically, which is the reliable headless trigger (natural-language routing is not).
- `--permission-mode` accepts `acceptEdits`, `auto`, `bypassPermissions`, `manual`, `dontAsk`, `plan`. For a non-TTY read-only run, `dontAsk` suppresses prompts and tracks denials rather than granting everything. `bypassPermissions` and `--dangerously-skip-permissions` grant everything and are not the default.
- `--allowedTools` / `--disallowedTools` (both spellings accepted) take tool patterns and gate tool access non-interactively. `--model`, `--append-system-prompt`, `--add-dir`, `--session-id`, `--max-budget-usd`, and `--fallback-model` exist; there is no `--max-turns` in this version. The process exit code is `0` on success and `1` on failure, which is the reliable programmatic success signal.
- `claude -p` auto-discovers the cwd's `.claude/` (skills, hooks, settings) and `CLAUDE.md`, so a run from the workspace root inherits the real skill set and guards.

The genuine design judgment is not the flags. It is that a headless run removes the human from the loop, and the single most important control in this workspace, stated in `.claude/rules/lethal-trifecta.md`, is that outbound send is ALWAYS human-gated. An unattended skill that could email or message would defeat that control precisely where it matters most. So the whole design is organized around one invariant: the headless runner structurally cannot send.

## Decisions

1. **`heading skill <name> [args]` is the headless verb, kept distinct from `heading run <script>`.** F-10.1's `run` dispatches a Python script and is vendor-independent. `skill` executes a Claude Code skill through `claude -p "/<name> <args>"` and is vendor-coupled by nature (a skill is model-interpreted content; it cannot run without the vendor runtime). One CLI, two clearly separated verbs, so the coupling boundary is legible: scripts are portable, skills are not.

2. **The runner is a guarded wrapper over `claude -p`, exit-code-primary.** It builds `claude -p "/<skill> <args>"` with `--output-format json` in the workspace cwd (so `.claude/` and `CLAUDE.md` auto-load), captures the process, and treats the exit code as the authoritative success signal (`0` ok, non-zero fail). The JSON envelope is parsed defensively for a result string and an error flag when present, purely as enrichment, because the envelope schema is undocumented and must not be a load-bearing dependency. If the `claude` binary is not on PATH, the runner exits non-zero with a plain message rather than hanging (the console-first degrade-clearly rule).

3. **Structural send gate: a headless run can never send. This is the load-bearing decision.** The runner passes a `--disallowedTools` set that blocks every outbound transport (the `send-email.py` Bash path, any telegram send, and the Action Queue `approve` path that turns a draft into a sent message). A headless skill may therefore DRAFT and deposit a `gated` Action Queue card, but that card still waits for a human to type `approve` in the terminal, exactly as `.claude/rules/tiered-risk.md` mandates. No permission mode and no flag the runner sets can approve a gated card. The push-time `content_scan()` wall and the `send_capable -> gated` code invariant remain the backstops, so the control does not rest on the disallowed-tools list alone.

4. **Default-deny allowlist, driven by existing frontmatter.** Only skills the runner is cleared for run headless. The machine signal is the frontmatter the orchestrator already reads: `x-heading-orchestration.parallel_safe: true` (read-only or isolated output) is headless-eligible; `partial`, `false`, and any `disable-model-invocation: true` skill are refused in this slice. The walking-skeleton allowlist is a single read-only skill, `state-check`. The allowlist is data that can only RAISE friction; the send gate (Decision 3) is code that sets the floor. This mirrors the tiered-risk shape: data cannot lower a control below its coded minimum.

5. **Permission mode `dontAsk`, never `bypassPermissions`; the skeleton ships the draft tier.** `dontAsk` is non-TTY safe and least-privilege: it suppresses prompts and records denials instead of granting everything. The skeleton's tool policy is the DRAFT tier (resolved 2026-07-09): `--allowedTools` permits reading, writing artifacts under the data root, and depositing a `gated` Action Queue card, while `--disallowedTools` blocks every send transport and the `approve` path (Decision 3). So a headless skill can produce a draft and queue it, and the send still waits for a human. The single allowlisted skill in this slice, `state-check`, is read-only and serves as the smoke skill; the draft-tier tool policy is present from the start, so a draft-capable skill added later needs only an allowlist entry, not a policy change. `bypassPermissions` and `--dangerously-skip-permissions` remain non-default.

6. **Data seam reuse, plus an explicit file-access grant.** Two SEPARATE mechanisms govern a headless run and must not be conflated. The env-var data seam (`WORKSPACE_ROOT` / `HEADING_OS_DATA`, as F-10.1 resolves it) drives PATH RESOLUTION for the `data-path-redirect.py` hook and the Python helpers. Claude Code's file-tool SANDBOX is a distinct gate limited to cwd plus `--add-dir`. The env seam alone grants no file access, so the runner also wires `--add-dir <data_root>` when the data root differs from the workspace root: a skill's inputs (`state-check` reads `context/current-data.md`, `context/pipeline.md`, `outputs/operations/workspace/...`) live under the data root, which the hook rewrites OUTSIDE cwd, and without the grant a headless read is denied under `dontAsk`. The grant is read-only in scope, so it does not widen the send boundary; the demo `examples/` default (F-10.2) needs no grant. The runner adds no data-resolution logic of its own beyond this one grant.

7. **Cost and prompt safety rails.** The runner sets a conservative `--max-budget-usd` cap (default 0.50 USD, overridable per call) so a runaway headless turn cannot burn unbounded spend, and optionally injects a short `--append-system-prompt` reminder that the run is headless and draft-only (do not wait for input, do not attempt to send). Both are guardrails, not logic.

8. **Walking-skeleton scope.** `heading skill state-check` runs headless and returns a structured result plus a correct exit code; the runner ships the draft-tier tool policy (write and queue-deposit allowed, send and `approve` blocked); tests assert the constructed command carries the send-blocking `--disallowedTools` set, permits the draft tools, and refuses a non-allowlisted skill before any `claude` call; the `claude`-absent path degrades with a non-zero exit and a plain message. No cron wiring and no `partial` phase-splitting in this slice.

9. **A narrow `propose` tier for `/odin reflect --propose` (resolved 2026-07-17).** Decision 4 refused every `parallel_safe: partial` skill outright as the simplest safe default at the time -- a reasonable first cut, not a considered verdict on `/odin` specifically. Misha directed a re-review: the actual invariant Decision 3's send gate protects is outbound send, and graduating an episode into a principle is an internal brain write, not a send. The `draft` tier (Decisions 5, 8) already proves the safe shape for "an unattended run can produce something consequential but cannot execute the terminal action" -- `queue-draft` drafts an email, cannot send; the `propose` tier drafts a reflect proposal, cannot graduate. Applying that pattern to Odin closes a real gap without weakening anything Decision 3 or `tiered-risk.md` protects.

   Mechanism: the allowlist schema grows from `{skill: tier}` to `{skill: {tier, args_prefix}}` so `odin` is admitted for exactly one invocation shape (`args_prefix: ["reflect", "--propose"]`), refused before any vendor call for every other mode. The tier's write grant is Claude Code's native path-scoped `Edit(//<abs-path>/**)` permission pattern (confirmed: gates `Write`/`Edit`/`NotebookEdit` together; a `Read` deny does NOT cover `Write`), naming ONE proposal-output directory, with an explicit `Edit(...)` deny for `knowledge/odin-brain/**` as belt-and-suspenders. Both patterns are built absolute (`//`-anchored from `get_data_root()`) since the headless process's cwd is the engine workspace root, not the data root where the brain and the proposal directory actually live. The automatic weekly trigger (wired into `odin-cadence-notify.py`) is gated behind an opt-in env var (`ODIN_REFLECT_PROPOSE_ENABLED`), unset by default; a manual `heading skill odin reflect --propose` invocation is never gated by it, since typing the command is already the deliberate CEO act the flag exists to preserve for the *automatic* path.

   **Council-confirmed finding: vendor-CLI tool permissions are one enforcement plane, not three independent layers.** An architecture stress-test (`/council`, 2026-07-17; Grok and Claude converged, no dissent) found that the propose-write allow, the odin-brain deny, and the send-deny are all enforced by the SAME engine (Claude Code's own permission checker) -- a parser bug, path edge case, or version regression collapses all three at once. Unlike Decision 3's send gate, which never trusts a single enforcement layer (`tiered-risk.md`'s `tier_for()` resolver floors a tampered config to `gated` in code, independent of the config), the propose tier had no equivalent second, independently-implemented check. **Fix: an integrity-check backstop.** `odin-cadence-notify.py`'s automatic-trigger wiring snapshots `knowledge/odin-brain/` (file paths, sizes, mtimes -- plain Python, no vendor-CLI dependency) immediately before and after every headless propose run; ANY detected change is a CRITICAL failure, logged loudly, and withholds the proposal path from that week's Telegram line. This is the tier's second, independently-implemented layer, mirroring `tiered-risk.md`'s "the ledger is data, the send-gate is code" pattern.

   **Council-confirmed finding: content-poisoning outranks unauthorized-write as the live threat.** The tool restriction already handles WHERE the model can write; the real risk is WHAT lands in the one file it is authorized to write. Raw episodes can carry untrusted third-party text (ingested via `learn`/`collect` from emails, web scrapes); if clustering quotes source episodes verbatim for grounding, that text can appear in the proposal nearly unchanged, and a reviewer skimming a routine weekly file may not notice a plant. **Fix: a provenance-marking requirement.** The `--propose` mode-catalog spec requires quoted source excerpts to be wrapped in a blockquote citing the source episode filename, visually distinct from Odin's own synthesized prose, so a reviewer can tell what is drafted versus quoted at a glance.

   **This tier's control set is an EXCEPTION specific to `odin reflect --propose`, not a template.** The council also flagged precedent drift: a working propose tier risks being cited to justify the next, looser piece of headless automation. It is not. The general instruction this establishes: future headless-automation candidates get the same review Decision 9 applied here -- is the actual invariant at risk, or only a broader-than-necessary default? -- AND a check for whether a second, independently-implemented (code-level, not vendor-permission-level) backstop is cheaply available, the way the integrity-check snapshot was here. A candidate that cannot get an equivalent backstop needs its own, separately-argued review before shipping, not a citation of this decision.

   **Accepted, documented, out-of-scope follow-on: OS-level sandboxing.** Both council voices recommended running the tier in a process sandbox (container/namespace, proposal-path-only writable, episode tree read-only, brain unmounted, vendor flags demoted to defense-in-depth on top) as the more rigorous write boundary. This is a real architectural escalation beyond a single narrow tier and was not built here; the integrity-check backstop closes most of the practical gap at a fraction of the cost. Recorded as a named follow-on hardening idea for this tier specifically, should the integrity-check prove insufficient in practice -- not a requirement for this decision's scope.

## Alternatives considered

- **Re-implement each skill as pure Python so no `claude` binary is needed:** rejected. A skill is model-interpreted content; a Python re-implementation is a fork that drifts from the skill and throws away the reason skills exist. The honest boundary is Decision 1: scripts are portable, skills are vendor-coupled.
- **Default to `bypassPermissions` / `--dangerously-skip-permissions` for a frictionless headless run:** rejected. It breaks least-privilege and puts the send gate one config slip away from open. Decision 5 keeps `dontAsk` plus a tool allowlist, and Decision 3 keeps the send gate in code regardless.
- **Allow any skill to run headless:** rejected on sovereignty grounds. Default-deny with an allowlist (Decision 4) is the safe direction; a skill earns headless eligibility, it is not granted by default.
- **A separate `heading-skill` script instead of a subcommand:** rejected. F-10.1 established a single `heading` invocation surface on purpose; a second entry point fragments it.
- **Rely on the JSON envelope as the success signal:** rejected. The envelope schema is undocumented; Decision 2 makes the exit code authoritative and the envelope best-effort, so a vendor change to the envelope cannot silently break failure detection.

## Resolved open questions

All four resolved by the operator on 2026-07-09.

1. **Skeleton allowlist.** Resolved: `state-check` only. It is cleanly read-only and serves as the smoke skill; the allowlist expands once the send-gate test is proven.
2. **Draft tier in the skeleton.** Resolved: ship the draft tier now. The runner's tool policy allows writing artifacts and depositing a `gated` Action Queue card from the start (send still human-approved). `state-check` is read-only and will not exercise the draft path, but the policy is present so a draft-capable skill added later needs only an allowlist entry (Decision 5).
3. **Budget cap default.** Resolved: `--max-budget-usd` defaults to 0.50 USD, overridable per call.
4. **Verb name.** Resolved: `heading skill <name>`.

## Engine and data boundary

Everything F-10.3 produces is engine-side and public: the `heading skill` subcommand, its allowlist logic, and its tests. The runner invokes the vendor `claude` binary and ships no private data. The data seam binds at runtime through `HEADING_OS_DATA`, never a copy, and resolves to the public demo `examples/` tree when unset. The send gate (Decision 3), the push-time `content_scan()` wall, and the `send_capable -> gated` invariant continue to gate what can leave the machine, and they gate a headless run too, because a headless skill runs the same guarded tree an interactive session does.

## Relations

- Depends on F-10.1: reuses the `heading` CLI surface (adds the `skill` verb next to `run`) and the `WORKSPACE_ROOT` / `HEADING_OS_DATA` data seam.
- Composes with F-10.2: an unconfigured headless run resolves to the read-only demo `examples/` tree, the same data-less default a freshly installed plugin sees.
- Enforces `.claude/rules/lethal-trifecta.md` and `.claude/rules/tiered-risk.md`: the send gate is the reason the runner exists in this shape, and the design adds no path around the human approve click.
- Honors `.claude/rules/console-first.md`: the runner is a terminal-native path that degrades clearly when the vendor binary is absent.
- Design-phase acceptance: this doc answering the headless-mechanics and sovereignty questions, plus a walking-skeleton `heading skill state-check` that runs the skill headless, returns a structured result and a correct exit code, refuses a non-allowlisted skill before any `claude` call, carries the send-blocking `--disallowedTools` set (asserted by a test), and degrades on an absent `claude` binary. No cron wiring and no write-capable tier yet. That is the scope of the `/implement` cycle that follows operator sign-off on this record.

## Delivery surface (Step-16 close-out, 2026-07-17)

The `propose` tier's automatic weekly trigger needed a live delivery surface. When the tier first shipped, its wiring lived in `odin-cadence-notify.py`, but nothing invoked that script on a schedule (`odin-cadence.timer` had been disabled since 2026-06-26, and `ops-radar.py` reads `odin-cadence.py` directly, never the notify script). Resolution (option **C+**):

- A dedicated weekly systemd-user timer **`odin-propose.timer`** (Monday 05:31, `{{TZ}}`-pinned) runs `scripts/odin-cadence-notify.py --propose-only`, installed by `scripts/install-odin-propose-timer.sh` with all three reboot-survival mechanisms (`Persistent=true`, `enable`, `loginctl enable-linger`).
- The new **`--propose-only`** mode skips the counts nudge (ops-radar already surfaces the counts daily — sending them again would be duplicate noise) and delivers to the CEO's Telegram DM ONLY a real outcome: a standalone, phone-readable DATA-relative proposal path, or the CRITICAL integrity alert. Otherwise it is silent.
- The propose flow was extracted to `_run_headless_propose(root) -> Optional[Path]`; `_maybe_headless_propose` stays a behavior-preserving wrapper for the normal path. The integrity backstop (Decision 9) is unchanged.
- **Rejected alternatives:** option A (re-enable `odin-cadence.timer` — re-creates a duplicate weekly counts nudge) and option B (fold the check into `ops-radar.py` — breaks its read-only daily-aggregator contract and mismatches the weekly cadence).
- Known follow-up (out of scope): `--propose` deliberately does not advance `.last-reflect`, so an un-acted cluster is re-proposed each week. Acceptable at weekly cadence; a dedup-against-existing-proposals pass would be needed before any higher frequency.
