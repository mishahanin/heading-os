# ADR F-10.1: package HEADING OS as Claude Code plugins and a marketplace

Design record for Phase 10 item F-10.1: how to distribute the engine as installable Claude Code plugins from a marketplace, generated from the monorepo, without rewriting the engine or coupling the whole catalog to a single vendor variable.

Last Updated: 2026-07-09
Status: accepted

## Context

Distribution today is clone plus WSL plus uv plus wizard, an afternoon of work. The Claude Code plugin ecosystem reduces "try it" to two commands: add a marketplace, install a plugin. That is the difference between an impressive repository and an installable platform, and it composes with the demo tier shipped in F-10.2.

The plugin mechanics were verified live against Claude Code v2.1.201 (official docs at code.claude.com/docs/en/plugins, plugin-marketplaces, plugins-reference, hooks). The load-bearing facts:

- A plugin is a directory. `.claude-plugin/plugin.json` is optional; when present, `name` is the only required field. Component dirs auto-discover at the plugin root: `skills/<name>/SKILL.md`, `agents/`, `hooks/hooks.json`, `.mcp.json`, `bin/` (added to Bash PATH), `settings.json`. `commands/` is the legacy flat-markdown form; new plugins use `skills/`.
- A marketplace is a git repo with `.claude-plugin/marketplace.json` declaring `name`, `owner`, and a `plugins` array. Each plugin entry has a `source`, which can be a relative path (resolved against the marketplace root), a `github` repo, a `url`, `git-subdir` (sparse clone, built for monorepos), or `npm`.
- Install is `/plugin marketplace add owner/repo` (or a local path `./dist/marketplace`), then `/plugin install <plugin>@<marketplace>`. Both a slash form and a `claude plugin ...` CLI form exist.
- Marketplace plugins are copied to `~/.claude/plugins/cache`, one dir per version. Files outside the plugin dir are not copied, so a repo-relative path to a bundled script breaks after install.
- `${CLAUDE_PLUGIN_ROOT}` is the documented, stable (not experimental) absolute path to the installed plugin dir. It substitutes inline in skill content, agent content, hook commands, and MCP configs, and is exported to hook and MCP subprocesses. It is the intended way to reach a bundled script. It changes on every plugin update, so it is ephemeral; persistent state uses `${CLAUDE_PLUGIN_DATA}`.
- A plugin `SessionStart` hook can persist an env var for the whole session by appending to the file at `$CLAUDE_ENV_FILE` (`echo 'export HEADING_OS_DATA=...' >> "$CLAUDE_ENV_FILE"`). A `userConfig` entry of type `directory` prompts the operator for a path at enable time.
- Plugin hooks run unsandboxed at the user's trust level, the same as the current `.claude/hooks/` set, but only fire once the plugin is enabled (`enabledPlugins`).

The three questions the playbook flagged as genuinely hard, restated against these verified facts, are the scripts-path coupling, the data seam in plugin form, and how to keep the monorepo as the source of truth. Two were verified to have clean native answers; the third is where the one real design judgment sits.

## Decisions

1. **Generation, not migration. The monorepo stays the source of truth.** A new `scripts/dev/build-plugins.py` assembles `dist/plugins/*` from the existing tree by a manifest that maps skills, the scripts they call, and `scripts/utils/` into bundles. The engine tree is never restructured for plugin shape; the plugin form is a build artifact. The marketplace file is generated the same way, mirroring the existing `generate-skill-router.py` pattern (registry generated from `SKILL.md` frontmatter, never hand-edited).

2. **Solve the scripts-path coupling with `${CLAUDE_PLUGIN_ROOT}`, and let the build do the rewrite.** In the monorepo a skill calls `python scripts/foo.py` (repo-relative, which is what the devcontainer and headless paths also use). `build-plugins.py` rewrites those references to `python "${CLAUDE_PLUGIN_ROOT}/scripts/foo.py"` in the built plugin only. This keeps the ~94 in-repo `SKILL.md` files unchanged and runnable as they are, while the packaged plugin gets the correct install-dir path. The rewrite targets `SKILL.md` (the documented-supported substitution surface); it deliberately avoids the legacy `commands/` markdown path, which has a live substitution bug (anthropics/claude-code issue #9354).

3. **Adopt Option C (hybrid) for vendor resilience: the native variable plus a thin `heading` CLI, both built now.** The plugin happy path uses `${CLAUDE_PLUGIN_ROOT}`, which is confirmed low-risk. As a hedge against a Claude Code change that ever breaks that variable, and as the invocation surface the monorepo, devcontainer, and headless (F-10.3) paths need anyway, the same `scripts/` are also reachable through a thin `heading` CLI (a uv tool that dispatches over the existing scripts, resolving paths through `get_workspace_root()` and the data-root seam). The CLI is a dispatcher, never a fork of script logic. Operator decision (2026-07-09): build the hybrid now, in F-10.1 scope, rather than defer the CLI to F-10.3, so the resilience hedge is live from the first walking skeleton and F-10.3 inherits a ready invocation surface. One smoke test runs a representative script both ways so the two surfaces cannot silently diverge.

4. **Ship the data seam as a plugin `SessionStart` hook plus a `userConfig` directory.** The hook resolves the operator's data root exactly as `paths.py` does and appends `export HEADING_OS_DATA=...` to `$CLAUDE_ENV_FILE`, so every session Bash call sees it. The operator supplies their private overlay path once via a `userConfig` entry of type `directory`. With no data configured, the seam resolves to the bundled read-only `examples/` demo, matching the F-10.2 first-run behavior. No private data ships in any plugin.

5. **Sovereignty hooks ship as plugin hooks, but the push-time wall stays the backstop.** The leak-guard, engine-guard, and secret-scan hooks ship as plugin `PreToolUse`/`PostToolUse` hooks with no capability loss (plugin hooks run unsandboxed at user trust). Because a plugin hook fires only when the plugin is enabled, security-critical hooks install user-scope with `defaultEnabled: true`, and the non-bypassable push-time `content_scan()` (already pure code on the sanctioned push path) remains the guarantee, not the plugin hooks.

6. **Bundle cut lines: a sovereignty core plus five capability bundles.** `heading-core` carries the rules, hooks, router, guard scripts, and the `prime`/`state-check`/`checkpoint` family (the sovereignty and session layer). Then `heading-intel`, `heading-comms`, `heading-content`, `heading-crm`, `heading-ops`. Each capability bundle declares the heavy extras its scripts need in its install docs, fed by the existing `x-heading-requires` frontmatter (F-7.1).

7. **Versioning: omit `version` during active development.** With no `version` in `plugin.json`, each commit is a new version and installs update automatically, which fits an actively-developed fleet. Switch to an explicit bumped `version` only when release-gated updates are wanted. `version` is never set in both the manifest and the marketplace entry (the manifest silently wins).

8. **Sequencing: `heading-core` alone first.** Build and install `heading-core` from a local marketplace path on the operator's machine, validate on a second machine, then expand bundle by bundle. No publish in the design phase.

## Alternatives considered

- **A separate `heading` CLI as the only interface (Option B):** rejected. It drops the native zero-config plugin experience that is the whole reason to ship as a plugin, and it is fragile in its own way (if `heading` is not on PATH in the plugin's execution environment, the happy path breaks for a self-inflicted reason). Option C keeps the native path and adds the CLI as a shared, second-duty artifact.
- **Rely solely on `${CLAUDE_PLUGIN_ROOT}` (Option A):** rejected as the sole strategy. The variable is low-risk, but a rename or removal is low-likelihood-high-blast-radius, and the monorepo, devcontainer, and headless paths get no shared entry point. Since F-10.3 must build that entry point anyway, the marginal cost of the hedge is near zero.
- **Bundle a copy of the needed scripts into each plugin, duplicating them per bundle:** rejected. It duplicates `scripts/utils/` across bundles and drifts. The `${CLAUDE_PLUGIN_ROOT}` rewrite plus a per-bundle script manifest keeps one script body.
- **Hand-edit every `SKILL.md` to use `${CLAUDE_PLUGIN_ROOT}` directly:** rejected. It breaks in-repo, devcontainer, and headless execution (where the variable is unset) and touches ~94 files. The build-time rewrite (Decision 2) keeps both worlds working from one source.
- **A single git-subdir source per plugin:** viable and kept as an option for the publish phase, but for the design-phase local build a single generated marketplace with relative-path sources plus `metadata.pluginRoot` is simpler. The publish topology is an open question below.

## Resolved open questions

All four were resolved by the operator on 2026-07-09.

1. **Marketplace host at publish time.** Resolved: (a) a separate `heading-os-marketplace` git repo receives the generated `dist/plugins/*` via the sanctioned push flow, keeping the engine repo free of built artifacts. The design phase stays local-only (`/plugin marketplace add ./dist/marketplace`); the separate repo is the publish target, wired in a later phase.
2. **Sovereignty hooks in the first walking skeleton.** Resolved: include the guard hooks in `heading-core` from the start (they define the layer). Validate `enabledPlugins`/`defaultEnabled` behavior on a second machine before any publish.
3. **Marketplace name.** Resolved: `heading-os-marketplace` (a distinct name, clear of the reserved `claude-plugins-official`, `anthropic-*`, `claude-community` set). Install form becomes `/plugin install heading-core@heading-os-marketplace`.
4. **CLI build timing.** Resolved: build the hybrid now, in F-10.1 scope. The `heading` CLI ships with the first walking skeleton alongside the native `${CLAUDE_PLUGIN_ROOT}` path, so the resilience hedge is live immediately and F-10.3 inherits a ready invocation surface.

## Engine and data boundary

Everything F-10.1 produces is engine-side and public: `build-plugins.py`, the generated `dist/plugins/*` and marketplace file, the bundle manifest, and the eventual `heading` CLI. No plugin carries private data. The only data-shaped thing a plugin ships is the public, illustrative-only `examples/` demo tree (shared with F-10.2). The data seam binds at runtime on the user's machine through `HEADING_OS_DATA` (a pointer set by the SessionStart hook plus `userConfig`), never a copy. The push-time `content_scan()` wall and the engine leak guards continue to gate what can leave the machine, and they gate the built plugins too, because the plugins are assembled from the engine tree those guards already cover.

## Relations

- Depends on F-7.1 (the core-plus-extras dependency split and `x-heading-requires` frontmatter feed each bundle's install docs) and reuses the F-5.1 generation pattern (`generate-skill-router.py`) for producing the marketplace file from `SKILL.md` frontmatter.
- Composes with F-10.2 (the demo tier is the data-less default a freshly installed plugin resolves to) and with F-10.3 (the headless runner inherits the same stable `heading` CLI invocation surface that Decision 3 builds now; F-10.1 ships it, F-10.3 reuses it).
- Design-phase acceptance: this doc answering the five playbook questions, plus a walking-skeleton `heading-core` (the sovereignty core: rules, guard hooks, router, and the `prime`/`state-check`/`checkpoint` family) generated by `build-plugins.py`, validated with `claude plugin validate --strict`, and installable from a local marketplace path (`/plugin marketplace add ./dist/marketplace`; `/plugin install heading-core@heading-os-marketplace`) on the operator's machine, PLUS the thin `heading` CLI with a smoke test proving a representative script runs identically the repo-relative way and the `heading` way. No publish and no separate `heading-os-marketplace` repo yet. That is the scope of the `/implement` cycle that follows operator sign-off on this record.
