# ADR F-10.2: demo mode and a zero-setup devcontainer

Design record for Phase 10 item F-10.2: how a newcomer gets from a bare clone to a running read-only skill in about ten minutes, and what actually remains to build given that demo mode already exists.

Last Updated: 2026-07-09
Status: accepted

## Context

Phase 10 is about platform legibility. The sharpest test of it is the first ten minutes: a stranger clones the public engine and wants to see it do something real without first standing up a private data repo, filling a `.env`, or paying for an API call. F-10.2 is that first-run experience.

Research into the current tree shows demo mode is already largely built, as a byproduct of earlier work:

- `examples/` is a committed, read-only demo data tree (`crm/`, `threads/business/`, `knowledge/`, `context/`, `outputs/`, a `README.md`, and a `.schema-version`). The README already describes it as "a read-only demo data tree for a data-less clone".
- `scripts/utils/paths.py` resolves the data root in three steps: a `HEADING_OS_DATA` env override that points at a real dir, then the `../.heading-os-data` sibling, then a read-only demo fallback that emits a warning. It also exposes `data_root_is_demo()`, and `get_instance_config()` falls back to engine-shipped `*.example.*` config so a data-less clone runs on bundled config.
- `docs/assets/demo.sh` is a working read-only recipe (it sets `HEADING_OS_DATA` to `examples/`, prints the resolved root and demo flag, then runs `crm-health.py`, the engine behind `/crm radar`) with no API and no model calls. It is what the README `demo.svg` terminal recording is rendered from.

What is missing is the packaging. There is no `.devcontainer/`, so "clone and run" still means installing WSL or a local toolchain, `uv`, the right Python, and the dependency set by hand. The demo path exists but is not the path a newcomer is handed.

## Decisions

1. **Do not rebuild demo mode; package it.** The data-root demo fallback, `examples/`, and `demo.sh` are real and sufficient. F-10.2 is scoped to (a) a devcontainer that makes the demo path the default first-run, and (b) documenting the ten-minute path. It does NOT change `paths.py` resolution or the `examples/` tree beyond what the container needs.
2. **The devcontainer defaults to demo mode.** The container image sets `HEADING_OS_DATA` to the in-repo `examples/` tree so a freshly opened container resolves to demo data with the existing warning, and every read-only skill works with zero configuration. A user who wires a real data repo overrides the env var, exactly as today.
3. **Zero-cost, read-only first run.** The documented ten-minute path runs only the commands `demo.sh` already proves safe (no API key, no model call, no outbound send). The container does not bake in any secret and ships no `.env`.
4. **Build on the real toolchain, not a parallel one.** The image uses the same `uv`-managed Python and the same `uv sync` extras path the project already uses (per CONTRIBUTING and DEPLOYMENT), so the container is not a second, drifting install recipe. A `postCreateCommand` runs `uv sync` and then the demo recipe once, so the first thing a user sees is the demo output.

## Alternatives considered

- **A separate "demo" data repo or a generator script:** rejected, `examples/` already is the demo tree and the fallback already resolves it. A second source would drift.
- **A Docker Compose / full daemon stack in the container:** rejected for the first-run scope. The ten-minute wow is a read-only skill, not the bridge daemon or mail sync. Daemons stay out of the devcontainer default (console-first: they are optional even locally).
- **Baking API keys or a model endpoint into the container for a "fuller" demo:** rejected outright. It would ship a secret and violate the zero-cost, read-only guarantee. The demo is deliberately model-less.

## Open questions

1. **Devcontainer base image.** Recommendation: the Microsoft `mcr.microsoft.com/devcontainers/python:3.11` base plus a `uv` install feature, over a hand-rolled Dockerfile, for Codespaces compatibility and low maintenance. Operator decides.
2. **Which extras the container syncs.** Recommendation: core `uv sync` only (the demo path needs no capability extras), keeping the image small and the build fast; document `uv sync --all-extras` as the next step. Operator decides.
3. **Where the ten-minute path is documented.** Recommendation: a short "Try it in 60 seconds" section in `docs/QUICKSTART.md` plus a "Open in a devcontainer / Codespaces" note in `docs/DEPLOYMENT.md`, rather than a new page. Operator decides.

## Engine and data boundary

Everything here is engine-side and public: `.devcontainer/`, `examples/`, `paths.py`, `demo.sh`, and the docs. The demo data in `examples/` is illustrative only and contains no real entities. The container ships no `.env`, no `.sessions`, and no real data; it resolves to `examples/` precisely because there is no private overlay in a fresh clone.

## Relations

Depends on the already-shipped demo-fallback in `scripts/utils/paths.py` and the `examples/` tree. Precedes no other Phase 10 item. Independent of F-10.1 (plugins) and F-10.3 (headless runner), though a devcontainer would later be a convenient host for both.
