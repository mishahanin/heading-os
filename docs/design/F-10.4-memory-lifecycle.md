# ADR F-10.4: One map for six memories + a unified memory CLI

Design record for Phase 10 item F-10.4: why the memory lifecycle gets one published map and one console-first command namespace, and the decisions taken before implementation.

Last Updated: 2026-07-08
Status: accepted

## Context

The engine has six memory mechanisms, each documented in isolation. What no single page shows is the lifecycle: which store is written when, and which script or hook moves data between stores, on what trigger and cadence. That knowledge lives only in code and scattered pages, and it is the highest concept-load part of the system for a newcomer or the future operator. Phase 10 is about platform legibility, so F-10.4 turns the implicit lifecycle into one diagram plus one command surface.

## The six stores (nodes)

All are DATA-side (private) except the code index, which is engine-side.

1. **auto-memory**: `<data-root>/auto-memory/*.md` plus the `MEMORY.md` index. The canonical durable home, written during sessions.
2. **native harness store**: the per-launch Claude Code native memory directory. Ephemeral, per clone.
3. **semantic recall index**: `<data-root>/.memory-index/` (business, ceo-only corpus: Odin brain, business threads, business CRM) and engine-side `.memory-index-code/` (code corpus). Built and queried by `scripts/memory-index.py` (`build` / `query` / `stats`; hybrid dense bge-m3 plus sparse FTS5 BM25 fused by reciprocal rank fusion).
4. **ODIN brain**: `<data-root>/knowledge/odin-brain/`. Managed by `/odin` and the `odin-*.py` family (compile, pagerank, lint, cadence).
5. **knowledge base**: `<data-root>/knowledge/` (plus `knowledge/shared/`, corporate). `/zk`.
6. **threads**: `<data-root>/threads/business|personal/`. `/thread`. Business threads feed the memory-index business corpus.

## The actors that move data (edges), verified in-tree

| Edge | Script or hook | Trigger and cadence |
| --- | --- | --- |
| session writes a memory | Write tool during a session | on demand |
| native store to/from canonical | `.claude/hooks/memory-reconcile.py` | SessionStart hook, newest-wins, NEVER propagates deletions |
| ~~retire past-due `expires:` records~~ | ~~`scripts/memory-auto-retire.py`~~ | RETIRED 2026-08-08, see below |
| retire a named record from all stores | `scripts/retire-memory.py` | manual, on explicit operator instruction, the only delete that sticks |
| rebuild the semantic index | `scripts/memory-index.py build` | daily 03:30 incremental |
| detect memory rot | `scripts/memory-hygiene.py` | weekly Monday 07:34, detect only, never mutates |
| promote a knowledge note to corporate | `scripts/promote-knowledge.py` | manual |
| consolidate (merge, delete, reword) | `/dream` | manual, human-gated |
| read-only health | `knowledge-health.py`, `odin-brain-health.py`, `memory_health.py` | on demand |

The playbook cited `memory-reconcile.py` at `scripts/`; the real path is `.claude/hooks/memory-reconcile.py`. The reconcile mechanism is real: it syncs the native per-launch store with the canonical DATA auto-memory, newest-wins, and never propagates deletions, which is why `retire-memory.py` (all-store) exists as the delete that sticks.

**Superseded 2026-08-08 — the auto-retire edge is retired.** Clock-driven retirement of auto-memory is switched off: auto-memory is never pruned, a memory that has gone unused sinks in recall ranking and stays retrievable, and removal happens only on an explicit operator instruction. `/dream` no longer stamps `expires:`, so the pass's only trigger no longer accrues, and `scripts/install-memory-auto-retire-timer.sh` refuses to install the timer unless the directive is deliberately overridden. The script and its unit templates stay on disk; switched off is not removed. Every other edge in the table above still holds.

## Decisions

1. **Mechanism-only diagram, no real content.** The map names stores and the scripts that move data; it embeds no real memory records, so it is engine-routed and publishable while the memory content stays DATA-private.
2. **Edges are the real scripts and hooks, verified in-tree.** No invented edge; `reconcile` is real and its no-deletion-propagation property is stated on the page so a reader does not expect a delete to sync.
3. **CLI is a pure shell-out facade, zero behavior change.** `scripts/memory.py` dispatches to the existing scripts and returns their exit codes. The one subtlety is `reconcile`: a bare arg-less call to the hook is hook-stdin mode and no-ops, so the facade must call it in CLI mode with resolved `--native` and `--canonical`. The facade resolves those paths but changes no behavior. If the native harness dir cannot be resolved reliably, `reconcile` is dropped rather than shipped as a no-op.

## Resolved open questions

1. **Diagram rendering on the docs site.** Chosen: vendor a pinned `docs/assets/mermaid.min.js` and inject it per-page only where a `mermaid` fence is present, with the generator emitting `mermaid` fences as `<pre class="mermaid">`. This keeps one text source of truth (the fence renders on GitHub and the site), needs no build step, stays offline and CSP-clean, and leaves every non-diagram page byte-identical and zero-JS. Rejected: a pre-rendered SVG (needs a Node render step and manual re-render) and a plain code-block fallback (the site would show no picture).
2. **Build the CLI now.** Chosen: build it. All six targets exist, the facade is pure shell-out, and it is a console-first discovery win.
3. **`status` aggregation.** Chosen: `memory-index.py stats` plus `knowledge-health.py` plus an auto-memory file count, all read-only, in human mode for a console-clean overview. The hygiene detector is deliberately excluded from `status`: it compiles the ODIN brain and takes minutes, which would break a quick overview, so it stays a dedicated `memory.py hygiene` subcommand. This refines the pre-implementation recommendation (which had listed hygiene under `status` and `--json` output); the substance (fast read-only signals) is preserved.

## Engine and data boundary

auto-memory, `knowledge/`, `threads/`, the ODIN brain content, and the `.memory-index` store are DATA-side and private. The scripts, the hook, the docs page, and the CLI are engine-side and public. The lifecycle page describes the mechanism only, with illustrative store names, so nothing private leaves the data overlay.

## Relation to F-10.1

`scripts/memory.py` is a deliberate precursor to the F-10.1 plugin `heading` CLI that would own `scripts/`. Keeping it a thin dispatcher makes that later fold-in trivial. It is not that CLI, and this ADR does not design it.
